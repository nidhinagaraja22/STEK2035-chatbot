STEK 2035 Chatbot - Cloud Environment Setup & Troubleshooting Notes
=====================================================================
(JupyterLab / data-lab.site cloud instance - "vault" folder)


THE CORE PROBLEM: EPHEMERAL CONTAINERS
---------------------------------------
Every time a new JupyterLab session/terminal is opened on this platform, it
can spin up in a DIFFERENT, FRESH container (different hostname each time,
e.g. jovyan@b146943d671e vs jovyan@47cf4d265f85). Only the `~/vault` folder
is persistent storage - everything else, including `$HOME/.bashrc` and any
env vars exported in a terminal, is WIPED between sessions.

This means:
  - Software installed outside ~/vault disappears between sessions.
  - `export` commands and `.bashrc` edits do NOT survive a new session.
  - Any background process (like `ollama serve`) dies when its session ends
    and must be restarted manually in a new session.

The fix: install everything INSIDE ~/vault (persists), and keep a small
setup script inside ~/vault that you re-run at the start of every new
session to restore PATH/env vars and restart background services.


ONE-TIME SETUP (already done)
-------------------------------
Ollama binary + models were installed into a persistent location:
  ~/vault/local/bin/ollama          <- the binary
  ~/vault/local/models/             <- OLLAMA_MODELS points here (pulled models live here)
  ~/vault/local/lib/ollama/         <- shared libraries

Models already pulled here: qwen2.5:32b (19 GB)


ONE-TIME SETUP - Node.js/npm INSIDE ~/vault (persists across resets)
--------------------------------------------------------------------
`sudo apt install nodejs npm` does NOT persist (installs outside ~/vault -
wiped on next container reset). Use the portable Linux binary instead,
extracted straight into ~/vault, same pattern as the Ollama binary:

  mkdir -p ~/vault/local
  cd /tmp
  curl -fsSL https://nodejs.org/dist/v22.14.0/node-v22.14.0-linux-x64.tar.xz -o node.tar.xz
  tar -xJf node.tar.xz -C ~/vault/local --strip-components=1
  rm node.tar.xz

This drops `node`, `npm`, `npx` into ~/vault/local/bin/ - already on PATH
via setup_env.sh below, no separate npm/node install step needed.

IMPORTANT: also clone/keep the project repos themselves inside ~/vault
(e.g. ~/vault/STEK2035-Chatbot_FrontEnd/stek-chatbot), not in $HOME or /tmp,
so `node_modules` from `npm install` survives container resets too.


ONE-TIME SETUP - Python deps INSIDE ~/vault (persists across resets)
----------------------------------------------------------------------
A venv created outside ~/vault (e.g. in $HOME) is wiped on reset, same
problem as everything else. Create it inside ~/vault instead:

  python3 -m venv ~/vault/local/venv
  source ~/vault/local/venv/bin/activate

  # backend (FastAPI RAG server)
  pip install -r ~/vault/STEK2035-chatbot/backend/requirements.txt

  # topic modeling + benchmark script deps
  pip install gensim spacy pyyaml pandas scikit-learn pymupdf sentence-transformers
  python -m spacy download de_core_news_sm
  python -m spacy download de_core_news_lg

Since the venv itself lives in ~/vault, everything pip/spacy installs into
it (including the downloaded spaCy language models) persists automatically
- no extra steps needed beyond activating this venv each session.


THE PERSISTENT ENV SETUP SCRIPT
----------------------------------
Created once, lives inside ~/vault so it survives container resets. Covers
Ollama, Node/npm, and the Python venv together:

  cat > ~/vault/local/setup_env.sh << 'EOF'
  export PATH="$HOME/vault/local/bin:$PATH"
  export LD_LIBRARY_PATH="$HOME/vault/local/lib/ollama:$LD_LIBRARY_PATH"
  export OLLAMA_MODELS="$HOME/vault/local/models"
  source "$HOME/vault/local/venv/bin/activate"
  EOF


EVERY NEW SESSION: STARTUP CHECKLIST
---------------------------------------
Run this at the start of every new terminal/session, before using
ollama/node/python:

  source ~/vault/local/setup_env.sh
  cd ~/vault/local && nohup ./bin/ollama serve > ollama.log 2>&1 &
  sleep 2
  ollama list
  node -v && npm -v
  python -c "import fastapi, gensim, spacy; print('python deps ok')"

`ollama list` should show qwen2.5:32b (and any other pulled models). If it
comes back empty or the serve command errors, see Troubleshooting below.
If `node -v`/`npm -v` or the python import check error out, the venv or
node install didn't actually land inside ~/vault - redo the one-time setup
steps above for whichever one failed.


TROUBLESHOOTING: "ollama list" SHOWS NO MODELS
-------------------------------------------------
Symptom: `ollama serve` background job shows "Exit 1" immediately (not
after running a while), and `ollama list` returns only the empty header
with zero rows (no error).

Most likely cause: a STALE `ollama serve` process is already running from
earlier in this session, started BEFORE `OLLAMA_MODELS` was set. It's still
bound to port 11434 and quietly serving from the default (empty) models
path, so your new serve attempt fails instantly with "address already in
use" -> exit 1, and `ollama list` talks to the OLD process which finds
nothing.

Fix - kill the stale process and restart clean:

  # 1. Check the actual log for the real error first
  cat ~/vault/local/ollama.log

  # 2. Look for an existing ollama serve process
  ps aux | grep "[o]llama serve"

  # 3. Kill it
  pkill -f "ollama serve"
  sleep 1

  # 4. Re-source env and start fresh
  source ~/vault/local/setup_env.sh
  nohup ~/vault/local/bin/ollama serve > ~/vault/local/ollama.log 2>&1 &
  sleep 2

  # 5. Confirm
  ollama list

If cat ollama.log shows something OTHER than "address already in use",
it's a real startup error (permissions, missing library in
LD_LIBRARY_PATH, etc.) - read that message specifically rather than
assuming it's the stale-process issue.


OPEN ITEM: GPU VISIBILITY NOT YET CONFIRMED
-----------------------------------------------
Earlier `ollama serve` startup logs showed:
  source=types.go:50 msg="inference compute" id=cpu library=cpu ...
  source=routes.go:2040 msg="vram-based default context" total_vram="0 B"

This means Ollama was only seeing a CPU compute device, NOT a GPU, despite
this being a cloud instance expected to have 40GB+ VRAM. If this container
truly has no GPU passthrough, large models (qwen2.5:32b, gemma2:27b, etc.)
will be extremely slow to generate.

To check: run `nvidia-smi` in the terminal.
  - Command not found / errors -> no GPU attached to this container; you'd
    need to select a GPU-enabled compute profile on the data-lab platform
    when launching the environment (this is a platform setting, not
    something fixable from inside the container).
  - Shows a GPU -> the GPU exists but Ollama isn't finding it (usually a
    CUDA_VISIBLE_DEVICES or driver/library path issue) - paste the
    nvidia-smi output for further diagnosis if this happens.


INSTALL COMMANDS - npm, Next.js, Python dependencies
---------------------------------------------------------

On the CLOUD instance: use the vault-persistent setup above (Node.js/npm
and Python venv sections) so nothing needs reinstalling every session, then:

  # fastapi + uvicorn[standard] are already in backend/requirements.txt,
  # installed as part of the Python venv setup above - explicit line here
  # in case you skipped requirements.txt and want just these two:
  pip install fastapi "uvicorn[standard]"

  npm install --prefix ~/vault/STEK2035-Chatbot_FrontEnd/stek-chatbot
  npm run dev --prefix ~/vault/STEK2035-Chatbot_FrontEnd/stek-chatbot

  cd ~/vault/STEK2035-chatbot
  uvicorn backend.rag_server:app --port 8000
  python assign_lda_topics.py    <- regenerate LDA topic assignments

On your LOCAL Windows machine instead (not the cloud - no ephemeral-
container issue here, a normal one-time install is fine):

1. Frontend - Next.js (npm)
   cd f:\Downloads\STEK2035-Chatbot_FrontEnd\stek-chatbot
   npm install
   npm run dev

2. Backend - Python (FastAPI RAG server)
   cd f:\Downloads\STEK2035-chatbot
   python -m venv venv
   venv\Scripts\activate
   pip install -r backend\requirements.txt
   uvicorn backend.rag_server:app --port 8000   <- run from repo root, not backend\

3. Topic modeling - extra Python deps
   pip install gensim spacy pyyaml pandas scikit-learn pymupdf
   python -m spacy download de_core_news_sm
   python -m spacy download de_core_news_lg
   python assign_lda_topics.py

4. Ollama - local LLM (separate installer, not pip/npm)
   https://ollama.com/download
   ollama pull qwen2.5:1.5b
   ollama serve

---------------------------------------------------------------
Script: benchmark_grid.py (repo root, alongside vector_store/chunks.jsonl)

Grid:
  Embedding models: multilingual-e5-base, multilingual-e5-large, bge-m3
  LLM models:       qwen2.5:32b, mistral, mistral-small, command-r, gemma2:27b
  Questions:        10 representative German STEK 2035 questions
  = 150 total generations, results saved incrementally after each
    embedding-model stage (safe to Ctrl+C partway through).

  source ~/vault/local/setup_env.sh
  pip install sentence-transformers
  ollama pull mistral
  ollama pull mistral-small
  ollama pull command-r
  ollama pull gemma2:27b

Run:
  cd <repo root, e.g. ~/vault/STEK2035-chatbot>
  python benchmark_grid.py

Output:
  benchmark_results.json   - full raw answers for every combo
  benchmark_summary.txt    - avg retrieval score per embedding model,
                              avg generation time per LLM model
